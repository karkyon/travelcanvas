## 4. TravelCanvasの現行機能構造 — 調査で使う地図

| 予約・準備 | 旅行箱、予約/チケット/QR、メール・画像取込、持ち物、費用/精算、文書 | 予約と予定の関連、OCRの人手確認、権限/機密度、重複候補、再試行状態 |

## 5. 競合比較レポートの結論を実装要件へ落とす

競合は公開説明を根拠とする比較であり、実アカウントを使った操作時間の比較や利用者調査ではない。Wanderlog(地図+旅程、共同編集、予算/持ち物)、TripIt(確認メールからの旅程取込)、Roadtrippers(道路旅行の地図/stop)、Google Maps(現地検索・保存・ナビ)の個別機能をまねることではなく、TravelCanvasの強みである相談から旅の記録までの連続性を完成させる。

### P0 — 全画面で「現在地・進捗・次の一手」を一貫させる

- 旅行状態を検討中/計画中/出発前/旅行中/旅行後として同一語彙で出し、焦点の旅行、残作業、次に得られる結果を同じplan文脈で示す。
- 同じ準備項目をHome、旅行箱、旅程、当日で重複計算・別名表示しない。APIの根拠・更新時刻を確認し、完了していない項目を完了扱いにしない。
- 各画面に主操作を1つ定め、完了後は次の操作へ進む/元の場所へ戻る導線を作る。閲覧のみ・ゲスト・オフラインでも押せるふりをしない。

### P0 — 場所検索から旅程反映までの文脈を保つ

- 今回のラベル改善を基準に、Home/共通レール/旅行内ナビ/プランナー/候補箱/全体検索/行きたい場所ライブラリで用語と説明を揃える。
- 「検索結果(未保存) → この旅行の候補(未確定) → 日・時刻を選んで旅程へ」の段階と保存先を表示。旅行、日、検索語、地図の中心を保持し、戻る操作で再選択を求めない。
- 採用後に旅行の正規Place IDが予定に残ること、保存/追加結果が候補とタイムラインへ反映されること、Undo後に候補が一貫することをソースから追う。失敗時に孤立イベントを作らない。

### P0 — データの確からしさを共通表示する

- `実データ / 手入力 / 概算 / 未照会 / 未接続 / 取得失敗` を混ぜず、値の隣に表示する。出典と取得時刻がある場合にだけ示す。
- 地図上の直線距離と道路経路、推定所要時間と実ナビを区別する。失敗したproviderを「0件」と表示しない。
- 各外部検索CTAの近くで、送る情報・送信先・保存有無・利用者操作を明示する。現在地は利用者操作後のみ取得する。

### P1 — 旅行箱を関連データの入口にする

- 予約/チケット/文書/領収書と該当予定の双方向リンクを整える。未関連データには「どの予定にも未リンク」と理由と関連付け操作を示す。
- 予約取込の抽出値・原本・不確かな値・重複候補・確認待ち/失敗/再試行を区別する。原本を確認せず予約に確定しない。

### P1 — 旅程と旅行相談の段階を整理する

- 初期の旅程画面は日程、地図、予定編集、次の操作を優先し、共有/出力/詳細設定は関連文脈の中へまとめる。既存機能を消さず、モバイルで主作業を先に出す。
- 旅行相談は入力→確認→方面比較→候補→未確定の旅程案→確定の順序と、確定前に作られるデータ/作られないデータを明示する。AI/道路/宿/混雑が未接続なら期待を持たせない。

### P2 — 実利用での理解度を測る

- 360/390px・タブレット・PCで主要経路、キーボード/読み上げ、200%文字、位置許可拒否、低通信/圏外、外部検索障害を確認する。
- 初回から予定1件までの成功率、検索候補の旅程採用率、予約の予定到達率、概算/未取得の理解、共同投票から旅程反映率を測る計画を用意する。自動テストをユーザー調査の代わりと呼ばない。
