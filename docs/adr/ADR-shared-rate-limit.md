# ADR: 回数制限の共有(Gate S3)

- 状態: 採用(Gate S3)
- 前提: Gate S2 適用後
- 関連: セキュリティ整理(2026-10-17)SEC-12・SEC-15、監査 F07
- トレーサビリティ: `docs/trace/gate-s3-trace.md`

## 1. 背景

AI を使った攻撃は、多数の IP・多数の要求を休まず並べて、ログイン(パスワードリスト)・登録・共有リンクの合言葉を
試す。回数制限はプロセス内の dict/deque だけで数えていたため:

- 複数の worker・コンテナ(GCP の Cloud Run を複数台にした時)では、それぞれが別々に数え、上限がその数倍に緩む。
- 再起動で数が消える。空になったキーも残り、キーの数に上限が無い(偽の IP・メールでメモリを増やせる)。
- 拒否した回数を外から見られず、攻撃に気づけない。refresh には制限が無かった。

## 2. 決定

- **Redis(`REDIS_URL`。セッションと同じ)で数える**。sorted set の滑る時間窓。判定と追加を Lua スクリプトで1回の往復・
  原子的に行う(20並列で上限5なら、通るのは必ず5)。キーは `"<RATE_LIMIT_NAMESPACE>:rl:" + sha256(元のキー)`。
  元のキーはメール・IP を含むため、Redis に平文で残さない。全てのキーに期限(時間窓)を付ける。
- **Redis に届かない時はプロセス内で続ける**(全拒否は認証を止め、全許可は守りを無くすため)。30秒ごとに Redis を
  試し直す。プロセス内の予備もキーの数に上限(5万)を置き、空のキーを消す。
- **監視**: `/metrics` に `travelcanvas_rate_limited_total{kind}`(kind はキーの「:」より前。値は入れない)と
  `travelcanvas_rate_limiter_fallback_total` を出す。Runbook §3.7。
- refresh にも IP ごとの制限(`RATE_LIMIT_REFRESH`、既定 60/分)を付ける。
- 試験は既定でプロセス内だけを使い(CI の backend ジョブには Redis が無い)、Redis の試験は試験ごとの名前空間で行う。
- 数が再起動で消えなくなるため、パッチは E2E の前に `reset_all()` で制限だけを消す。

## 3. 範囲外・残り

- 異常の自動検知と段階的な対応(遅延→CAPTCHA→一時制限→通知、SEC-16/17)は次の Gate。
- 処理量・費用の上限(最適化・アップロード・エクスポート、SEC-13)、アップロードの隔離と検査(SEC-14)。
- 利用者ごと(認証後)の API 全体の制限は、上の検知と合わせて設計する。
