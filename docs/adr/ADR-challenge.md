# ADR: 段階的な計算の確認(proof of work)で、怪しい接続元の入口の費用を上げる(Gate S7)

- 状態: 採用
- 対象: セキュリティ整理 SEC-07(人間確認・ボット対策)
- 関連: `docs/adr/ADR-threat-guard.md`(Gate S6)、Runbook §3.10

## 背景

ログイン・登録・ゲスト開始は、ログインしていない誰でも呼べる入口で、AI を使った攻撃は多数の接続元から休まず試す。
回数制限(S3)と自動遮断(S6)は、遮断の閾値に届くまでは何もしない。CAPTCHA は外部サービス(鍵・通信先・
個人情報の送信)と画面の操作が要り、旅行中の利用者にも負担になる。

## 決定

1. 接続元の点数(S6)が `CHALLENGE_SCORE`(30)以上の時だけ、ログイン・登録・ゲスト開始・昇格に計算の確認を求める。
   難しさは `CHALLENGE_BASE_DIFFICULTY`(16ビット、平均約6.5万回)から、点数が `CHALLENGE_SCORE_STEP`(30)増えるごとに
   1ビット(2倍)上がる(上限24ビット)。
2. backend は 428 と、ヘッダー `X-TC-Challenge`(token)・`X-TC-Challenge-Difficulty` を返す。detail は普通の文字列のまま。
   token は HMAC 署名の自己完結の値(入口・難しさ・期限120秒・ランダムな値・接続元の IP の sha256)。DB は使わない。
3. 画面の APIクライアントが自動で `sha256(token + ":" + counter)` の先頭の 0 のビット数が難しさ以上の counter を探し、
   同じ要求を1回だけ送り直す(`frontend/src/utils/challengeSolver.ts`。同期の SHA-256、一定回数ごとに処理を手放す)。
   利用者の操作は増えない。
4. 検証: 署名・入口・期限・接続元・難しさ(発行後に点数が上がっていれば易しすぎる)・解・使い回し(Redis に記録、
   届かない時はプロセス内)。偽造・誤った解・使い回しは点数(`challenge_failed`、5点)にもする。
   解かずに送り続けるだけの要求も点数(`challenge_unsolved`、2点)にし、最後は遮断(S6)する。
   [Gate G10-Q] ただし、問題を出していない接続元・入口からの最初の1回の解なしの要求は点数にしない(画面は確認が要るかを
   知らないため、正しい利用者も最初は解なしで送る)。問題を出した後も解かずに送ってきた時だけ数え、解いて通ったら数え直す。
   以前は最初の1回にも点数を付け、同じ回線でログイン・登録を繰り返すと解いているのに遮断まで上がった。
5. 監視: `security_events_total{kind="challenge_issued|challenge_passed|challenge_failed"}`。
6. `CHALLENGE_ALWAYS` で、点数に関わらず常に求める入口を指定できる(攻撃が続く時の一時的な強化)。

## 採らなかったもの

- 外部の CAPTCHA(reCAPTCHA・Turnstile): 外部への送信・鍵の管理・画面の変更が要る。必要になれば、同じ 428 の仕組みに
  別の種類の確認として足せる。
- 常に求める: 普通の利用者の端末(古いスマートフォン)の負担になる。

## 影響

- GPU を使う攻撃者には安い。目的は「大量の試行の費用を上げる」ことで、遮断(S6)・回数制限(S3)と組み合わせる。
- 難しさ24ビットでは普通の端末で数十秒かかる(点数が非常に高い接続元だけ)。
