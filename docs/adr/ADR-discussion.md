# ADR: 合意形成(FR-022)・コメント(FR-024)の最小実装

- 状態: 採用(Gate P3)
- 前提: Gate P2(予算・費用・精算)適用後
- 関連: DOC-02 FR-022 / FR-024 / FC-065〜067・EX-011、DOC-05 §8.4、DOC-04 SC-19・SC-20
- トレーサビリティ: `docs/trace/gate-p3-trace.md`

## 1. 背景

FR-022(候補の投票と懸念の解消)・FR-024(コメント・メンション)はDB・API・UIのいずれも存在しなかった。
グループ旅行では「誰かが強く反対している案」を多数決で決めてしまうことが不満の原因になるため、
件数だけでなく懸念・不可(veto)とその解決を記録できることを重視する。

## 2. 決定

### 2.1 データ(migration `c9f4a2b7d1e3`、4テーブル新設のみ)

- `polls`(状態 open/closed、veto_policy、匿名、決定した選択肢、締切)、`poll_options`(最大10、予定への参照は任意)、
  `votes`(選択肢×利用者で一意。懸念・不可は理由必須をDB CHECKでも保証。解決の記録)、
  `comments`(対象 plan/event/reservation/poll/expense、返信は1段、メンション、未解決/解決済み)。
- すべて plan_id に ON DELETE CASCADE(B-012)。予定(events)・共同編集者への外部キーは張らない(B-013の方針)。
  予定が削除された選択肢は `event_missing` で示す。

### 2.2 合意の判定(`app/services/consensus.py`、consensus-v1)

- 回答は Love / OK / 懸念 / 不可 / 棄権。懸念・不可は理由が必須。
- veto_policy: `block`(不可1票で不成立)、`block_with_alternative`(不可には代替案も必須)、`advisory`(不可は参考意見)。
- 選択肢の状態: 未解決の不可=不成立、未回答者あり=回答待ち、未解決の懸念=懸念あり、それ以外=合意。
  締切後は回答者の中で判定する。状態は色だけでなく文字で示す。
- 「最有力」は点数(Love=2、OK=1、懸念=-1、advisoryの不可=-2)で決め、不成立の選択肢は選ばない。
- 決定は編集者以上が明示的に行い、決定と同時に締め切る(自動で決めない)。不成立の選択肢は決定できない(409)。
- 回答を変えると、その回答の解決記録は消える(解決した懸念が別の内容にすり替わらないようにする)。

### 2.3 匿名(FC-067)

- 匿名の投票では、本人以外に誰がどう回答したかを返さない。回答者が3人未満の間は件数・点数も返さない(`counts_hidden`)。
- 未回答者は表示する(参加の有無は回答内容ではないため)。

### 2.4 コメント(FR-024・EX-011)

- 予約番号・PIN・旅券番号らしき文字列(キーワード、8桁以上の数字、英数混在の6文字以上)があれば
  `sensitive_warning` で知らせる。保存は止めない(誤検出で相談が止まらないようにする)。画面は送信前にも注意を出す。
- メンションはプランのメンバーに限る。メンションした相手と投票作成時のメンバーに通知を作るが、通知・監査には本文を入れない。
- 削除は論理削除。返信がある親は「削除されました」と表示してスレッドの形を保つ。

### 2.5 API・権限

- 投票の作成・変更・締切・削除・決定: editor以上。回答・コメント: viewer以上。懸念の解決: 回答した本人かeditor以上。
- 回答は選択肢ごとの変更をまとめてPUTし、全件を検証してから保存する(一部だけ保存されない)。
- 変更・削除は If-Match(revision)による楽観ロック(428/400/409)。

## 3. 今回の範囲外

- 予定・予約・費用の画面からのコメント(APIは対象を受け付けるが、画面はプラン全体と投票のみ)。
- 決定した選択肢を予定へ自動反映すること(FR-022の「採用」)。現状は記録のみ。
- 締切前のリマインド通知、リアルタイム更新(再読込で反映)。
