# ADR: 不審な接続元の自動検知と段階的な自動遮断(Gate S6)

- 状態: 採用
- 対象: セキュリティ整理 SEC-16(異常検知)・SEC-17(自動の隔離)・SEC-18(監視・通知)・SEC-27(攻撃の型の回帰試験)
- 関連: `docs/adr/ADR-shared-rate-limit.md`(Gate S3)、Runbook §3.9

## 背景

AI を使った攻撃は、1件ずつ見れば普通の失敗に見える要求を、休まず大量に、入口を変えながら組み合わせて送る。

- パスワードリスト攻撃でメールを毎回変える(メールごとの回数制限に掛からない)
- 他人の ID を推測し、予約・文書・思い出・プランと入口を変えて探す(入口ごとの制限が無い・緩い)
- 偽のトークン・期限切れの文書 URL・別サイトからの操作を混ぜる

Gate S3 の回数制限は「入口ごと・キーごと」の数しか見ないため、こうした攻撃を止められなかった。

## 決定

1. 接続元(IP)ごとに、失敗した応答・防御が働いた出来事を重み付きの点数にし、15分の窓で合計する
   (`app/services/threat_guard.py` の `SIGNAL_WEIGHTS`)。応答の状態から分類するもの(401/403/404/413/429)と、
   ハンドラが明示的に伝えるもの(ウイルス・URL の拒否・別サイトからの操作)がある。
   成功した要求・ログインしていない画面の 401(トークン無し)・ID を含まない 404・監視の入口は数えない。
2. 段階的に対応する: 注意(60点、監査と計数)→ 遮断(150点、その接続元の `/api/*` を15分 429)→
   再犯(24時間以内なら4倍、上限24時間)。遮断で返した 429 は点数にしない(遮断が延び続けない)。
3. 状態は回数制限と同じ Redis(全プロセス共有、キーは sha256 で IP を残さない、期限付き)。
   届かない時はプロセス内(キー数に上限)で続ける。
4. 判定は request_id のミドルウェアの中(CORS より内側)で行い、429 にも CORS・セキュリティヘッダーを付ける。
   閾値を越えた時の監査(DB)はイベントループを止めないよう別スレッドで書く。
5. 監視(`tcops.py monitor`)は、自動遮断・拒否の急増(前回から50件以上)を注意、監査の書き込み失敗を異常として通知する。
6. 試験では既定で無効(`tests/conftest.py`。TestClient は全要求が同じ接続元のため)。
   `tests/test_gate_s6_threat_guard.py` が有効にして、攻撃の型ごとに止まること・普通の利用が止まらないことを確かめる。

## 採らなかったもの

- アカウント単位の自動ロック: 攻撃者が他人のアカウントを意図的にロックできる(サービス妨害)。
  アカウント側の対応は、refresh token の再利用検知による全セッション失効(Gate #28/S2)とパスワード規則(S2)で行う。
- WAF・外部サービスへの依存: 自前の環境(omega-dev2)と Cloud Run の両方で同じ動きにするため、まずはアプリ内で行う。
  前段に WAF・CDN を置く時は、本機能を補助として残す(`GUARD_TRUSTED_IPS` に前段を入れない。X-Forwarded-For は
  uvicorn の `--proxy-headers` と `FORWARDED_ALLOW_IPS` で正しい接続元にしてから使う)。
- CAPTCHA: 画面の変更と外部サービスが要るため別の Gate(SEC-07)。

## 影響

- 同じ NAT の後ろの多くの利用者が同時に大量の失敗をすると、まとめて止まり得る(Runbook §3.9 の外し方・閾値)。
- 遮断中は、その接続元の正規の利用者も15分使えない。誤検知の時は `threat_guard.reset(ip)`。
