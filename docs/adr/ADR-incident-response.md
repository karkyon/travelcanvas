# ADR: 侵害が疑われる時の封じ込めの操作(Gate S8)

- 状態: 採用
- 対象: セキュリティ整理 SEC-19(インシデント対応の手順)・SEC-20(封じ込めの手段)
- 関連: `docs/adr/ADR-threat-guard.md`(S6)、`docs/adr/ADR-challenge.md`(S7)、Runbook §8

## 背景

自動の防御(S3 の回数制限・S6 の自動遮断・S7 の計算の確認)は閾値で動く。攻撃が閾値の下で広く続く時、
利用者のアカウントが乗っ取られた時、鍵の漏洩が疑われる時には、運用者がすぐに防御を強め、
セッションを失効させる手段が要る。これまでは DB を直接書き換えるしかなく、手順も無かった。

## 決定

1. `app/services/incident.py`: 期限付きの警戒モード(Redis で全プロセス共有。最大7日)。
   - 全員のログイン・登録・ゲスト開始・昇格に計算の確認を求める(S7)
   - 自動遮断の注意・遮断の閾値を `GUARD_LOCKDOWN_FACTOR`(0.5)倍にする(S6)
   - 指定すれば新規登録・ゲスト開始を 503 にする(既存の利用者のログインは止めない)
   - 要求ごとに Redis を読まないよう、状態は5秒覚えておく
2. セッションの失効: 1人(メール)または全員。API は毎回セッションを確かめるため、アクセストークンも次の要求から使えない。
3. 操作の入口は運用者だけ: ホストの `tcops.py security …` → backend のコンテナの `scripts/security_incident.py`。
   画面・API からは使えない(乗っ取られた管理者アカウントから防御を外されない)。全ての操作を監査ログに残す。
4. Redis に届かない時、警戒モードは backend の全プロセスに伝わらないため、失敗(終了コード4)として返す。
5. Runbook §8 に、気付く→記録を守る→封じ込める→鍵を替える→戻す→振り返る の手順と、鍵ごとの替え方・影響を書く。

## 採らなかったもの

- 管理画面からの操作: 管理者の多要素認証(SEC-06)が無い間は、画面から防御を外せる経路を作らない。
- 暗号化の鍵の自動の切り替え: 保存済みのデータの再暗号化が要る(DB の変更)。別の Gate(SEC-F)。
