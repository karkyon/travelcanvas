# ADR: 運用の最小基盤(B-010: バックアップ・復元演習・監視・rollback)

- 状態: 採用(Gate O1、2026-10-16)
- 関連: DOC-10 §0.3・§7 B-010・§13、DOC-07(開発環境・運用環境)、DOC-11(暗号鍵・保持期間)、FR-004(完全削除バッチの定期実行)
- 手順書: `docs/ops/RUNBOOK.md`

## 1. 背景

DOC-10 r7 時点で、FR の91%にコードがあり71%が画面〜DBまで結線されているが、VERIFIED(完成)と
判定できる機能は0件だった。判定条件の「運用」の証拠(backup/restore・監視・Runbook・rollback 演習)が
1つも無かったため(B-010)。既存の `scripts/database/backup_db.sh` は古い構成(ホストの pg_dump と
`.env.local`)を前提にしており、docker compose 構成では動かず、復元の手順も検証も無かった。
完全削除のバッチ(`backend/scripts/run_*_purge.py`)も、定期実行の登録手順が無かった。

## 2. 決定

### 2.1 道具は1つの CLI(`scripts/ops/tcops.py`)

- 本体は `backend/app/ops/cli.py`、判定は `backend/app/ops/opslib.py` の純粋関数。**標準ライブラリだけ**で書き、
  ホストの `python3` から追加のパッケージ無しで動く。backend コンテナの pytest で同じ関数を検査できる。
- docker compose 経由で実行する(`compose` モード)。pg_dump/pg_restore は postgres コンテナ内で、
  件数・復号の点検は backend コンテナ内で動かす。**接続文字列とパスワードはコンテナの中で組み立て、
  ホスト側のコマンドライン・ログに現れない**(試験で確認)。
- サンドボックス・CI 向けに `local` モード(PostgreSQL のコマンドと backend の Python を直接使う)を持ち、
  同じ処理を通しで試験する(`test_local_drill_end_to_end`)。

### 2.2 バックアップ

- DB は `pg_dump -Fc`、保存ファイル(`/app/uploads`)は tar.gz、目録(manifest)は JSON。目録を最後に書き、
  目録の無いものは使わない。作成直後に目録とハッシュを照合し、合わなければ消して失敗にする。
- 目録に「取得の直前と直後の表ごとの件数」を残す。運用中の書き込みで件数が変わった表は、復元後の件数が
  直前〜直後の範囲なら「運用中に変化」として失敗にしない(pg_dump は1つのスナップショットで取るため)。
- 鍵は**バックアップに含めない**(同じ場所に置くと、バックアップの漏洩=暗号の無効化になる)。代わりに鍵の
  指紋(SHA-256 の先頭12桁)を目録に残し、復元時に今の鍵と比べて取り違えを検出する。
- 世代管理: 直近7日は各日1つ、直近4週は各週1つ、最低3つ。未来の日時のもの(時計ずれ)は消さない。
- 権限: 置き場所 0700、ファイル 0600(個人データを含むため)。

### 2.3 復元と演習

- **運用中の DB は上書きしない。** 復元先は名前に `restore` を含む別名の DB に限り、運用中の DB 名・`test` を
  含む名前は拒否する(誤って運用中の DB や試験用 DB を消さない)。切り替えは `.env` の `DATABASE_URL` の
  DB 名で行い、元の DB を残す(いつでも戻せる)。
- 演習(`drill`)で確認すること: 目録とハッシュ、pg_restore の成功、alembic の版の一致、表ごとの件数、
  保存ファイル(件数・ハッシュ、DBが参照しているのにファイルが無い記録の件数)、**暗号化列が今の鍵で
  復号できること**(`*_ciphertext` の各列から最大5件)、鍵の指紋の一致、復元先での migration の往復
  (最新を1つ downgrade → upgrade head、実データの上で downgrade が通ること)、1つ前の commit への
  rollback 計画、監視の取得。
- 記録(Markdown)は件数・ハッシュの先頭・所要時間だけで、個人データ・storage_key・接続文字列を含めない。

### 2.4 監視

- backend に `GET /metrics`(Prometheus のテキスト形式)を追加。ラベルは**ルートの型**だけで、実際のURL
  (旅行IDなど)は入れない。どのルートにも当たらない要求は `<unmatched>` にまとめ、ラベルの種類が利用者の
  入力で増えないようにする。`METRICS_TOKEN` を設定すると Bearer が必要、未設定時は私設アドレスからだけ。
  見せない時は404(存在を明かさない)。OpenAPI には載せない。
- `/ready` に `migration_current`(DB の版 = コードの migration head)を追加。従来は「何らかの版がある」
  ことしか見ておらず、`alembic upgrade head` の忘れ(新しい表が無いまま動く)や、コードだけ戻して downgrade
  を忘れた状態を ready と答えていた。
- `tcops.py monitor` を cron で5分ごとに実行し、/health・/ready・/metrics の増分(5xx・応答時間の95%点)・
  コンテナの状態・ディスク・バックアップと演習の鮮度を判定する。前回の観測を `ops-state/` に保存して
  増分を出し、backend の再起動(カウンタの減少)は誤検知しない。通知は状態が変わった時だけ(任意の webhook)。

### 2.5 定期実行

`tcops.py schedule install` が crontab に管理区画を1つだけ入れる(何度実行しても1つ、他の行は変えない、
`remove` で元どおり)。パッチは crontab を自動では変更しない(利用者の環境の恒常的な変更のため、
利用者が1度だけ実行する)。

## 3. 採らなかった案

| 案 | 理由 |
|---|---|
| prometheus_client を使う | 既定のグローバル登録がプロセス・試験間で状態を共有し、ルート型のラベル制御も自前で要る。50行程度の自前実装の方が検査しやすい |
| バックアップを Fernet で暗号化 | 鍵を同じ `.env` に置くと保護にならず、別鍵の管理(KMS)は未導入。権限 0600 と「鍵は別保管」で代替し、KMS 導入時に見直す |
| 運用中の DB へ直接 `pg_restore --clean` | 失敗すると運用中の DB が中途半端に壊れる。別名へ復元して切り替える方が、確認でき、戻せる |
| PITR(WAL の継続的な保存) | 個人開発の規模では日次の論理バックアップで足りる。RPO(失ってよいデータの量)は最大24時間 |
| systemd timer | omega-dev2 の利用者 crontab の方が、root 権限なしで登録・解除できる |

## 4. 未実装・制約

- バックアップの別の機械・クラウドへの複製(現状は同じ機械。`OPS_BACKUP_DIR` を別ディスクにすることを推奨)。
- redis はセッション・レート制限の一時データのみで、バックアップしない(失っても再ログインで回復)。
- 保存ファイルの中身の復号確認(文書・写真)は行わない(DB の暗号化列のみ)。
- Prometheus・Grafana・外部の監視サービスは未導入(`/metrics` の形式は対応済み)。
- SLO(目標の稼働率・応答時間)は未定義。
- backend のアプリケーションログの個人情報の自動検査(B-009)は別 Gate。
