# ADR: 外部状況(アラート)と安全な再計画(FR-030/FR-031)の最小実装

- 状態: 採用(Gate P10)
- 前提: Gate P9(アカウント削除・同意)適用後
- 関連: DOC-02 FR-030・FR-031、DOC-04 SC-24、DOC-06 §13、DOC-13 AlertReceived/ReplanReady/ReplanApplied、共通不変条件4(差分・理由・影響・承認・Undo)
- トレーサビリティ: `docs/trace/gate-p10-trace.md`

## 1. 背景

FR-031(問題イベントを起点に、固定予約を守る代替案A/Bを提示し、変更対象・通知対象・費用差・遅延差・失う予定を示し、
利用者承認前に共有旅程を変更しない)は全く無かった。FR-030(外部状況)は登録済み経路の運行状態を当日画面に出すだけで、
状況を記録して旅程への影響を扱う仕組み(alert/impact domain)が無かった。外部の運行情報・天気providerは未接続である。

## 2. 決定

### 2.1 データ(migration `f7a3d1c8e2b5`、2テーブル新設のみ)

- `plan_alerts`: 種類(delay/cancellation/closure/weather)・情報源(user_report/route_status と自由記述の source_label)・
  取得時刻(observed_at)・確度(confirmed/reported)・影響を受ける予定/日・遅れの見込み(15〜720分)・メモ・状態(active/resolved/dismissed)。
  予定・日への外部キーは張らない(B-013の個別削除を妨げないため。使う時に存在を確認し、削除済みなら「対象の予定は削除されました」と示す)。
- `replans`: アラート・作成時点の本案の版(base_revision)と予定(base_snapshot)・案A/B(candidates、JSON)・状態(proposed/applied/rejected)・
  適用した案・適用した変更セット(change_sets、ON DELETE SET NULL)。plan_id・alert_id は ON DELETE CASCADE(B-012の外部キー方針)。

### 2.2 外部状況の扱い(FR-030)

- 外部providerは未接続のため、状況は利用者の報告で登録する。登録済み経路(採用した経路候補)の区間の運行状態が遅延・運休の予定は
  「検出した状況」として一覧に出し、ワンタップで登録欄へ入れる(まだアラートにしていない予定だけ)。
- 取得時刻は必須(既定は登録時刻)で未来は不可。取得から3時間を過ぎた情報は `is_stale` とし、画面で「古い情報」と明示する
  (取得不能時に最後の値を現在値のように見せない)。

### 2.3 再計画案(replan-v1、`app/services/replan.py`)

- 守る予定 = 確定(ロック)済み、または予約(reservations.event_id / event_reservations)と紐付く予定。どの案でも時刻・日を変えず外さない。
  影響が及ぶ場合は注意(予約先へ連絡等)を示す。
- 外せない予定 = 予約・移動区間・経路候補・リンク・文書と紐付く予定。外す代わりに残して注意を付ける(紐付けを失わせない)。
- 遅延・運休: A「後ろの予定をずらす」(影響を受けた予定以降を遅れの分ずらす。守る予定の開始に重なる・日付を越える予定は外す。守る予定より後は元の時刻)、
  B「後ろの予定の時刻を守る」(影響を受けた予定だけ遅らせ、その予定時間に重なる予定を外し、後は元の時刻)。
- 休業・中止 / 雨天・警報(指定日の屋外の予定): A「外す」、B「翌日の同じ時刻へ移す」(翌日が無ければ使えない案として理由を示す)。
- 比較の値: 変わる予定(前→後の時刻・日)、外す予定、守る予定、最大の遅れ、その日の最後の予定の変化、
  外す予定に紐付く支払い済みの費用(基準通貨。換算できない分は件数)、通知するメンバー(操作した人を除く)。

### 2.4 承認と適用

- 再計画案を作っても本案は変えない。適用は If-Match(本案のrevision)と、案の base_revision が現在の本案と一致する場合だけ行う。
  変わっていれば409 `replan_stale`(作り直しを案内)。revisionが変わらない変更(予約の紐付けの追加)も適用前に再確認し、
  外す予定・動かす予定に紐付けが増えていれば409 `replan_conflict`。いずれも本案は変えない(黙って上書きしない)。
- 適用は P7 の分岐案採用と同じ処理(`branches_api.apply_ops`)で、1つの変更セット(source=replan、予約済みの値)として記録し、
  本案の「元に戻す」で全て戻る。戻した後は案を「適用後に取り消し」と表示する。適用したアラートは解決済みにする。
- 適用時に操作した人以外のメンバーへ通知する(DOC-04 SC-24「共同者へ差分通知」)。本文は件数だけで予定名は含めない。

### 2.5 権限

- 閲覧はviewer以上、登録・状態変更・再計画・適用・却下はeditor以上。アラートの変更・案の却下はそれぞれのrevision(If-Match)。
- 監査は種類・件数だけ(予定名・メモ・情報源の文言は記録しない)。

## 3. 今回の範囲外

- 外部provider(運行情報・天気・警報・休業)からの自動取得と、取得失敗時の扱い(provider接続のGateで行う)。
- 代替の移動手段・経路の自動探索、移動時間を考慮した案(内部推定の経路と組み合わせる最適化はL4以降)。
- 3案以上・部分採用・条件を変えた作り直し、リアルタイム配信(WebSocket)での即時通知、プッシュ通知。
- 予約の変更・取消の代行(AIは予約確定・支払い・重要変更を無確認で行わない、DOC-02 スコープ境界)。
