# ADR: 旅行・利用者ごとのデータ鍵と鍵の破棄による削除(Gate G3・SEC-F5/F6)

- 状態: 採用(2026-10-22)
- 関係: ADR-key-rotation(G1)、ADR-db-roles(G2)、docs/ops/KEY-INVENTORY.md §3

## 背景

G1 までの暗号化は1つの鍵(`ENCRYPTION_KEY`)で全ての値を暗号化していた。旅行・アカウントを消すと DB の行は消えるが、
バックアップ(過去の世代・別の場所の写し)には暗号文と、それを読める鍵が残る。監査の台帳(SEC-F5)は「鍵の破棄で、
DB・バックアップの写しのどちらからも読めないこと」を求める。

## 決定

1. **データ鍵(DEK)** を対象ごとに1つ持つ: 旅行(`plan`)・利用者(`user`)。旅行の中身(予約・チケット・秘匿制約・持ち物・
   予算・しおり・文書・取り込みの候補・旅の記録のファイル)は旅行の鍵、秘匿プロフィールと位置の軌跡は利用者の鍵。
   組織の Webhook の秘密(個人データでない)・QuickDraft(短命で自動で消える)は `ENCRYPTION_KEY` のまま。
2. データ鍵は `ENCRYPTION_KEY`(KEK)で包んで `data_keys` に持つ。KEK の切り替えは `data_keys` の行の包み直しだけ。
3. 暗号文の形は `tc2:dek:<鍵のID>:<Fernet>`。以前の形(封筒なし)も読む。移し替えは `rekey convert --to envelope`、
   戻しは `--to legacy`(前のコードへ戻す前)。
4. 破棄は削除と同じ取引で行う(旅行の完全削除・アカウントの削除)。包んだ鍵を NULL にし、日時と理由だけを残す。
5. **バックアップ**は `data_keys` の行をダンプに入れず、鍵の写し `<ID>.keys.jsonl` を別に置く。破棄した鍵は
   `keys purge-escrow`(毎日・バックアップの直後)が全ての世代の写しから消し、目録のハッシュも直す。
   復元は写しから鍵を入れる。破棄した鍵の値は「消した」(erased)と数え、失敗にはしない(記録の無い鍵は失敗)。
6. **TOTP の秘密**(SEC-F6)は別の鍵 `MFA_KEY`(版つき、`MFA_KEYS_PREVIOUS`)で包む(`tc2:mfa:<版>:…`)。
   多要素認証の解除は申請と別の管理者の承認(本人は申請も承認もできない、24時間で期限切れ)。

## 理由・代わりの案

- 値ごとの鍵(per-value DEK)は鍵の数が多すぎ、検索の索引(HMAC)と合わない。対象ごとが削除の単位と一致する。
- KMS(SEC-F3)を待たずに導入できる。KMS を入れる時は KEK を KMS へ移すだけで、データ鍵の仕組みは変えない。
- 鍵の読み書きは要求の取り消しと別に確定する(鍵だけが残っても害は無いが、鍵が消えて暗号文が残ると読めない)。

## 限界

- 破棄から `keys purge-escrow` までの間(最大1日)、その日のバックアップの写しには鍵が残る。外部へ写した写しは、
  purge の後に写し直す運用が要る(Runbook §8.9)。
- 1つのプロセスは鍵を最大5分記憶する。破棄の時に同じプロセスの記憶は消すが、他のプロセスでは最大5分残る
  (破棄する時には行そのものも消えているため、読まれる値は無い)。
